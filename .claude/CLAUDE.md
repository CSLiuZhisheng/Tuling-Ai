# Tuling-AI 项目开发规则

## 🎯 核心原则

简单性、性能、可维护性不是对立关系。设计时先明确约束，再选择满足约束的最小复杂度方案；性能关键路径必须有目标、有验证，非关键路径避免过度设计。

### 1. 避免过度设计

- **KISS 原则**：在满足功能、性能、可维护性等明确约束下，选择复杂度最低的可行方案。
  - 性能是设计约束，不是事后才考虑的问题；
  - 对关键路径、外部调用、数据量大的场景，需要提前设定超时、容量、延迟目标；
  - 非关键路径避免为了“未来可能的需求”引入复杂抽象或过早优化。
- **YAGNI 原则**：只实现当前需要的功能，不要预测未来需求；但 YAGNI 不等于忽略非功能需求。
  - 当前已知的性能、安全、稳定性约束必须纳入设计；
  - 只是不提前实现当前不需要的业务功能和抽象层。
- **增量迭代**：先实现核心功能，验证后再扩展。
- **避免过早优化**：不要在没有指标和瓶颈证据时做局部微优化；但架构级、不可逆的性能风险必须在设计阶段评估。
  - 先保证正确性和可维护性；
  - 对已知高成本操作，如大模型调用、向量检索、批量数据处理，设计时就要考虑超时、并发、缓存和降级；
  - 优化应基于压测、日志、P99 延迟等证据，而不是凭感觉。
- **拒绝过度抽象**：不要为了“灵活性”引入不必要的抽象层。

**反例**：

```python
# ❌ 过度设计：为简单配置创建复杂的工厂模式
class ConfigFactory:
    def create_strategy(self, type): ...

# ✅ 简单直接：直接使用配置
config = {"timeout": 30}
```

### 2. 代码注释要求

#### 2.1 必须添加注释的场景

- **函数/方法**：说明功能、参数、返回值、异常。
- **复杂逻辑**：多步骤处理、算法、状态转换。
- **业务规则**：为什么这么做，背后的业务原因。
- **性能关键代码**：为什么选择这种实现方式。
- **临时方案/技术债**：用 `TODO`、`FIXME`、`HACK` 标注。

#### 2.2 注释示例

```python
def query_rag_with_retry(query: str, max_retries: int = 3) -> dict:
    """查询 RAG 知识库，带重试机制。
    
    Args:
        query: 用户查询文本。
        max_retries: 最大重试次数，默认 3 次。
        
    Returns:
        dict: 包含 answer 和 sources 的结果。
        
    Raises:
        TimeoutError: 查询超时（30 秒）。
        ConnectionError: RAG 服务不可用。
        
    Note:
        - 使用指数退避重试：1s, 2s, 4s。
        - 超时后会降级返回友好提示。
    """
    
    # 1. 验证查询长度（避免过长查询导致向量计算 OOM）
    if len(query) > 1000:
        raise ValueError("查询文本过长，最多 1000 字符")
    
    # 2. 重试循环
    for attempt in range(max_retries):
        try:
            # 调用 RAG API，30 秒超时
            result = await call_rag_api(query, timeout=30)
            return result
            
        except TimeoutError:
            # 超时重试，指数退避
            if attempt < max_retries - 1:
                wait_time = 2 ** attempt
                logger.warning(f"RAG 查询超时，{wait_time} 秒后重试...")
                await asyncio.sleep(wait_time)
            else:
                # 最后一次失败，返回降级响应
                logger.error("RAG 查询最终失败")
                raise
```

#### 2.3 注释风格

- **中文注释**：业务逻辑、复杂算法说明。
- **英文注释**：可选，团队有国际成员时使用。
- **文档字符串**：使用 Google 或 NumPy 风格。
- **行内注释**：解释“为什么”，而不是“做什么”。

```python
# ✅ 好的注释：解释原因
timeout = 30  # RAG 查询平均耗时 5s，P99 为 25s，设置 30s 防止极端情况

# ❌ 差的注释：重复代码
timeout = 30  # 设置超时为 30 秒
```

### 3. 代码实施要求

- **先计划后实施**：非平凡的修改需要先展示方案，等待确认。
- **小步提交**：每次改动聚焦单一目标，方便回滚。
- **测试驱动**：关键功能必须有测试用例。
- **渐进式重构**：不要一次性大范围改动，逐步优化。

### 4. 技术栈约束

- **语言**：Python 3.10+。
- **异步框架**：FastAPI + asyncio。
- **依赖管理**：优先使用项目已有的库，避免引入新依赖。
- **新增依赖**：必须说明理由和替代方案对比。

### 5. 错误处理

- **明确的错误信息**：告诉用户发生了什么，如何解决。
- **分层处理**：底层抛异常，上层捕获并转换为友好提示。
- **日志记录**：错误必须记录到日志，便于排查。

```python
try:
    result = await query_rag(text)
except TimeoutError:
    logger.error(f"RAG 查询超时: query={text[:50]}")
    return {"error": "知识库查询超时，请稍后重试"}  # 用户友好提示
except Exception as e:
    logger.exception(f"RAG 查询失败: {e}")  # 记录完整堆栈
    return {"error": "服务暂时不可用"}
```

### 6. 性能考虑

- **超时保护**：所有外部调用必须设置超时。
- **重试机制**：临时性错误需要重试，但要限制次数。
- **资源释放**：使用 `async with` 确保连接正确关闭。
- **避免阻塞**：CPU 密集任务使用 `asyncio.to_thread` 或进程池。
- **关键路径识别与验证**：对大模型调用、向量检索、批量数据处理等关键路径，设计阶段明确超时、并发、缓存和降级策略，并通过压测、日志、P99 延迟等证据验证；非关键路径避免过早优化。

## 🔧 开发流程

1. **理解需求**：确认要解决的问题。
2. **设计方案**：在满足功能、性能、可维护性等约束下，选择复杂度最低的可行方案。
3. **展示计划**：说明改动范围和理由。
4. **等待确认**：获得批准后再执行。
5. **实施变更**：小步提交，添加注释。
6. **测试验证**：确保功能正常。
7. **更新文档**：记录重要变更。

## ⚠️ 禁止事项

- ❌ 不经确认直接大范围重构。
- ❌ 引入未经讨论的新技术栈。
- ❌ 删除看似无用的代码（可能有隐藏依赖）。
- ❌ 提交未测试的代码。
- ❌ 复杂逻辑不写注释。

## 📝 Commit 规范

```text
<type>(<scope>): <subject>

<body>

<footer>
```

**提交类型**：

- `feat`：新功能
- `fix`：Bug 修复
- `refactor`：重构（不改变功能）
- `perf`：性能优化
- `docs`：文档更新
- `test`：测试相关
- `chore`：构建/工具链相关

**示例**：

```text
feat(langgraph): 添加 RAG 查询超时保护

- 为 knowledge_agent 添加 30 秒超时
- 添加重试机制（3 次，指数退避）
- 超时后返回降级响应

解决问题：RAG 服务假死导致请求永久阻塞
```

- **格式化**：遵循 PEP 8。

- **变量命名**：清晰表达意图，避免缩写。
